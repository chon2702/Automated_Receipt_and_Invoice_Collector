# goco: invoice retrieval feasibility

Research date: 5 November 2026. Scope: all 25 vendors in the project brief, with separate entries where product billing differs.

**Company evidence added:** The subsequently supplied card/vendor inventory reports actual email PDF delivery for several vendors left unverified in this public-documentation review. The company context and corrections are kept in the local inventory. Its account-specific observations refine the collection priorities below; they do not establish new public APIs or successful live collector tests.

## Recommendation

Start with email attachment collection, an AWS invoice API collector, and manual import. Use an existing authorized shared folder as the first destination if one is available. Keep the storage interface replaceable until Google Drive, Microsoft storage, or a company server has been selected.

This is a documentation-based feasibility assessment, not a tested integration inventory. No customer accounts were accessed, credentials requested, provider settings changed, or documents downloaded. A route described as documented still needs validation against goco's actual account, billing region, purchase channel, and permissions.

Do not promise unattended collection for all vendors. Email notifications can contain attachments, links, or just billing notices. A usage/cost API is not evidence that the original invoice can be downloaded. A provider using Stripe or Paddle does not give its customers access to the provider's merchant API keys.

## Reading the matrix

- **Documented**: official documentation describes the indicated capability. It has not been tested with a goco account.
- **Conditional**: a documented capability requires a particular agreement, purchase channel, or permission, or access provisioning is unresolved.
- **Unverified**: the reviewed material did not establish the capability. This does not mean the capability does not exist.
- **Email first**: inspect a real invoice message before accepting the vendor into automated coverage. Preserve attachments unchanged; record links as pending until a supported download route is validated.
- **Manual**: a person obtains the vendor's original file and imports it with account and period information.

In the API column, “unverified” always means actual invoice/receipt file retrieval, not whether the vendor has a general API. Unless explicitly noted, exact portal role names and automation permission remain unverified. Portal login requires an authorized user and any normal MFA; no browser route in this report has been approved or tested for unattended execution.

## Authentication and browser feasibility

For all portal-only entries, technical practicality, permitted automation, session lifetime, MFA behavior, CAPTCHA exposure, and stable original-file downloads remain untested. A visible Download button is not enough evidence to commit to a Playwright integration. Manual import provides coverage without making that commitment.

LinkedIn has an explicit automation restriction in its official guidance. Keep its browser collectors out of scope unless a supported, provider-authorized route becomes available. For other vendors, automation permission is unresolved, not presumed granted. Never reuse private browser endpoints as if they were official APIs.

For a future browser feasibility check, use a normal interactive login with the authorized account holder, stop when human authentication is required, protect the browser session as a secret, and verify the terms that apply to the actual product/account. Prefer original provider downloads over printing rendered portal pages. These are proposed evaluation criteria, not completed tests.

Email access is a reusable integration, with vendor-specific rules rather than 25 independent mailbox clients:

| Mail provider | Documented retrieval | Proposed minimum access | Open operational check |
|---|---|---|---|
| Gmail / Google Workspace | Message attachment retrieval through Gmail API. | OAuth `gmail.readonly` supports attachment access. It is a restricted scope and is mailbox-wide, not limited to the folder/label the app searches. | Confirm internal app registration, company consent rules and token lifecycle. Search filters are not a security boundary. [Attachment API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments/get), [scopes](https://developers.google.com/workspace/gmail/api/auth/scopes). |
| Microsoft 365 / Outlook | Microsoft Graph retrieves message attachments. | Delegated `Mail.Read` for the signed-in mailbox. Shared mailbox access requires separate permission/delegation design. | Confirm tenant consent and selected mailbox; avoid organization-wide application access for the two-user MVP. Prefer an existing dedicated invoice mailbox where practical; otherwise use separately authorized cardholder mailboxes. Do not select a mail provider before the company identifies its existing service. IMAP remains an alternative to investigate if neither API fits; its authentication and server capabilities have not been researched here.

## Proposed MVP scope for the next decision

These are recommendations inferred from the evidence above, not settled implementation requirements.

1. **Configuration and reporting:** distinguish vendor, product, billing account, owner/cardholder, purchase channel and billing cadence. One vendor can have multiple accounts; one invoice can cover multiple products/accounts.
2. **Manual import:** accept original files with explicit vendor/account/period metadata. This makes every vendor trackable even before it has an automated collector.
3. **One email provider:** implement only the company's actual provider initially. Pilot with two or three vendors whose real messages have usable originals; ElevenLabs, JetBrains, Workspace and Anthropic are candidates, not guaranteed attachment sources.
4. **One official vendor API:** AWS is the strongest initial candidate. Validate pagination, invoice-period selection, IAM permissions, multiple invoice entities, supplemental documents and expiring URLs against a real authorized account before calling it supported.
5. **Filesystem destination:** a configured local/shared path for the proof of concept. Preserve originals and adjacent portable metadata, then maintain a rebuildable local SQLite index. A local-only folder is a pilot destination; it does not fulfill central employee access until an authorized shared destination is configured and checked.
6. **Repeatable runs:** detect identical content with SHA-256 and identify business documents by vendor/account/document ID/type. Preserve corrections as separate versions; invoice and receipt are different records. Store multiple provenance references when email and API return the same document.
7. **Honest status:** show downloaded, already present, authentication required, failed, manual required, pending/not yet issued, and unknown expectations. Do not label a missing mailbox search result as proof that an invoice is missing.

Defer browser collectors, cloud hosting, schedules, notifications, OCR/AI extraction, direct Drive/SharePoint APIs, and broad API expansion. Keep amount/currency/date unknown when authoritative metadata is unavailable; importing a document must not depend on guessing its contents.

## Correctness details that affect realistic scope

**Missing-document expectations:** configure cadence, next expected issue date, grace period, active dates, expected document types and account identity. Annual renewals, usage thresholds, prepaid credits and zero-spend months do not follow a universal monthly-one-invoice rule. October service can produce a November-issued invoice. Define whether `--month` means service period or issue month, and store both where known. Completeness stays unknown where there is no reliable expectation; later card-transaction reconciliation would improve it but is a separate feature.

**Originals and storage:** retain PDFs, XML and other originals unchanged. Keep invoice versus receipt versus credit note versus statement explicit. If the email body is the original record, preserve its source message/MIME; any generated PDF is derived. Files should be written atomically and checked before metadata is marked collected. Exports/sidecars should carry account, owner, billing period, issue date, source identifier, document type and hash so SQLite is not the sole source of business context. Do not store expiring signed links in logs as durable records.

**Failures and credentials:** use OS credential storage or an approved secret manager for OAuth refresh tokens; YAML/JSON holds references only. Prefer SDK-managed short-lived AWS sessions. Expired consent/MFA produces an actionable authentication-required result. Retry temporary network/server/rate-limit failures with bounded backoff; isolate failures by account. Logs must omit passwords, tokens, signed URLs and full card numbers. Shared folder permissions and backup responsibilities are deployment decisions to validate, not properties Python can guarantee by writing a file.

## Account validation checklist before implementation

Record one row per actual billing account, with no credentials in the inventory:

- Vendor, product, account identifier, owner and authorized billing user.
- Direct purchase, reseller, app store or other purchase channel; billing region/entity and agreement where relevant.
- Monthly/annual/threshold/prepaid cadence and expected issue timing.
- Existing billing mailbox and an example message: attachment, linked file, body-only receipt or notification.
- A sample original invoice/receipt, document type and desired metadata; keep private samples outside version control.
- For API candidates: read-only credential provisioning, exact permissions, invoice visibility, history range, pagination and actual file retrieval.
- For unresolved vendors: confirm document delivery/download with billing contact or provider support. Prioritize Craft, Meta, netcup, PRM, Sprinto, t3n and any separate Celonis contract.

Remaining company choices: mailbox provider, central destination, account-to-cardholder assignments, completeness expectations, and the desired treatment of billing month versus issue month. These choices need no passwords or full card details and can be made after this research review.

## Pilot acceptance evidence

Before claiming a collector is supported, demonstrate an authorized retrieval of a real original document for the chosen period, verify its account/type, preserve its hash and provenance, rerun without creating a second copy, and show that expired authentication and temporary network errors yield actionable results without losing files. Demonstrate manual import through the same storage/reporting path, index recovery from portable metadata, and an unknown/pending outcome when invoice expectations cannot yet establish a missing document.

Research limitations: selected official sources and targeted searches were used; this is not an exhaustive audit of every vendor API, contract or terms document. Meta's official help/developer content was inaccessible. Other unverified rows explicitly remain open rather than being classified as unsupported. Refresh the relevant official documentation immediately before implementing each integration.
